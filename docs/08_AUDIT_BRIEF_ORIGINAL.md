Audiobook AI Workspace: Full UX, UI, Backend Flow Audit and Implementation Plan
You are acting as a senior product designer, UX architect, frontend engineer, and backend engineer. Your task is to audit the current Audiobook AI Workspace application deeply and practically. Do not assume how the app works. Inspect the current code, UI, database schema, frontend components, backend routes, job flow, state management, and actual user flows before making conclusions. The goal is to answer this core question:

How should the user experience work from the moment a user opens a book, reads a chapter, translates text, compares scripts, generates audio, listens, reviews versions, and exports the final audiobook? Do not skip any point below. First audit the current implementation, then explain what is wrong or confusing, then recommend what should be changed, and finally create a concrete implementation TODO broken into jobs.

Audit the Current Convert Flow Deeply inspect all places where the user can start conversion or generation. Check these flows: Convert from the left/sidebar narration panel Convert from a chapter row Convert from selected chapters or batch action bar Convert/generate from reading mode, if it exists Any settings modal opened from convert buttons Any gear/settings split button behavior Any hidden or duplicated conversion behavior Explain exactly what currently happens when each option is clicked. Check whether these actions are confusing, duplicated, not synced, or using different settings. Specifically check: Does row convert fire instantly while another convert button opens a modal? Are settings discoverable? Are sidebar convert, row convert, and batch convert consistent? Does batch conversion ignore per-chapter overrides? Does the UI clearly explain whether it is translating text, generating audio, or doing both? Does the user understand which button to use? Give a clear conclusion on whether the current conversion UX should be merged, renamed, moved, or redesigned.

Define the Correct Convert Model The app should not use one vague word, "Convert", for everything. Audit whether the app currently separates these actions: Translate Text Only Generate Audio Only Translate Text + Generate Audio Regenerate AI Script Generate Audio from Existing AI Script Generate Audio from Custom Script Generate Audio from Original Text Recommend the best final UX. The user should always know: What source text/script is being used What language is selected What voice is selected What style is selected Whether TTS cost/time will be used Whether the action creates text only, audio only, or both If a confirmation modal is needed, make it useful. If quick actions are needed, explain how they should remember book defaults using something like "Do not ask again for this book."

Audit Text, Script, and Audio Architecture Inspect the current backend and database schema. The product should have a clear mental model: Original Text: EPUB chapter text AI Script: text generated or translated by AI Custom Script: user-written or pasted narration text Audio Version: generated audio linked to the exact script used Audit whether the current database and backend correctly support this model. Check: Where original chapter text is stored Where AI translated text is stored Whether legacy translated_content is still used Whether chapter_scripts is used correctly Whether custom scripts can be stored safely Whether multiple scripts per chapter are supported Whether audio files link to the exact script_id Whether script versions are overwritten accidentally Whether the UI can show which script created which audio Whether audio version metadata is accurate Recommend schema or API changes if needed. The final rule should be:

Audio must always point to the exact script used to generate it.

Audit Text-Only Translation Flow Currently translation may be treated as a side effect of audio generation. Audit whether this is true. The app should support text-only translation because the user may want to review AI output before generating audio. Design the correct flow: User opens a chapter. User reads original text. User clicks Translate Text. App sends chapter text to GroQ or selected AI provider. App stores the result as an AI script. App does not generate audio. UI updates to show AI Script available. User can compare, edit, copy, or generate audio later. Inspect whether current backend routes and jobs support this. If not, create implementation tasks.

Audit Reading Mode and Script Comparison Analyze the reading mode deeply. The reading mode should allow the user to read peacefully and also work with scripts when needed. Check whether the current reading mode supports: Original text view AI script view Custom script view Comparison view Audio playback Current narration settings visibility Translate Text action Generate Audio action Translate + Generate Audio action Use Custom Script action Paste custom script directly Saving multiple custom scripts Selecting active script Deleting script versions Seeing which script is linked to the current audio Recommend the ideal reader layout. Suggested model: Tabs: Original, AI Script, Custom Script, Compare Original tab shows EPUB text AI Script tab shows generated AI text or an empty state with Translate Text Custom Script tab shows editor, paste button, save button, and script versions Compare tab allows Original vs AI, AI vs Custom, or Original vs Custom Decide whether three-way comparison is useful or too complex. If useful, recommend how to keep it advanced but not overwhelming.

Audit Custom Script Flow Inspect how custom script currently works. If the current flow uses extra dialogs like: User clicks custom script Then sees another popup Then clicks "Go to editor" Then pastes script Recommend removing unnecessary steps. The target UX should be: User clicks Use Custom Script App directly opens the Custom Script tab User can paste immediately User can click Paste from Clipboard If browser clipboard permission fails, UI says "Press Ctrl+V to paste here" User can save script User can generate audio from saved custom script User can keep one active script User can delete unused scripts Audit whether current database and UI support multiple custom scripts. If this makes the UI too complex, recommend a simple version first.

Audit Audio Player and Listening Pane Analyze the current audio player behavior and listening pane. The audio player should feel naturally integrated and always available when listening makes sense. Check: Where the current player appears Whether the player is only inside chapter rows Whether there is a persistent bottom player Whether reading mode has its own detailed listening pane Whether playback continues when user navigates Whether previous and next work correctly Whether seek bar exists Whether speed and pitch controls exist Whether speed and pitch reset incorrectly Whether selected audio version updates the visible script Whether user can download chapter audio from the player area Whether user can regenerate audio from the player area Recommend the correct player model. Audit Text and Audio Synchronization Analyze whether text/audio sync exists or should exist. Recommended behavior: Highlight-only mode: text highlights while audio plays, but scrolling does not seek audio. Sync navigation mode: clicking or double-clicking text seeks audio to that part, and playback scrolls/highlights the text. Check if alignment data exists, such as sentence-to-timestamp mapping. If alignment is unreliable, recommend making sync optional. Explain what database/API support is needed, such as storing alignment_json per audio file.

Audit Speed and Pitch Persistence Current issue: speed and pitch may reset when switching chapters. Audit the current state management and settings storage. Recommend final behavior: If user changes speed or pitch, keep it during the session. Add "Make default" inside the player. Add "Apply to this book" if book-level override is useful. Store global default in app settings or user settings. Store book-level override in book preset/settings if needed. Do not reset to 1x/default pitch every time chapter changes. Create implementation tasks for this.

Audit Batch Conversion Analyze selected-chapter and batch conversion behavior. Current concern: Batch conversion may ignore per-chapter overrides. User may be forced to manually convert chapters one by one. Recommend better behavior: Batch should calculate effective settings per chapter. Group chapters by identical settings. Create one job per settings group. Show summary before starting. Example: Group 1: Chapters 1, 2, 4 use Hindi, AI Script, Aria Group 2: Chapter 3 uses Custom Script, Madhur Group 3: Chapter 5 uses Original Text, English, Aria UI should explain:

This batch will create 3 generation jobs because selected chapters use different settings. Create implementation tasks if this is not supported.

Define Previous and Next Behavior Analyze the current previous/next playback behavior. Recommend the correct rule. Default behavior should be:

Previous and Next follow original chapter order, not current sort order. Explain exceptions: If user explicitly plays selected chapters, next/previous follows selected queue. If user explicitly plays visible filtered list, next/previous follows visible list order. If user plays normal book mode, next/previous follows chapter_index. Create implementation tasks if current behavior is wrong.

Audit Chunking Strategy Inspect how large chapter text is sent to GroQ and TTS. Explain the current chunking strategy if it exists. Audit: Where chunking happens Whether chunking happens before AI translation Whether chunking happens before TTS What chunk size is used Whether chunks break sentences unnaturally Whether chunks preserve paragraph boundaries Whether output is stitched correctly Whether logs show chunk progress Whether retry can happen per chunk Whether chunk IDs or chunk status are stored anywhere Recommend the correct chunking strategy with reasons. Suggested principle: Prefer paragraph-aware chunking. Do not split mid-sentence unless unavoidable. Translation chunks should preserve context. TTS chunks should respect provider limits. Store enough metadata to debug failed chunks if needed. Recommend schema/API changes only if necessary.
